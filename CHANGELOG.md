# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- Founding documentation: product, domain model, architecture decisions and roadmap.
- Application scaffold: Next.js (App Router), strict TypeScript, Tailwind CSS v4, ESLint, Vitest and the `lint`, `typecheck` and `test` npm scripts run by the CI.
- Storage layer: SQLite through Drizzle ORM, a first migration applied at startup, a configurable data directory (`DEMAIN_DATA_DIR`) and environment validation that stops the server when a required variable is missing.
- Money core: integer minor-unit amounts, text parsing without floating point (`1 143,88 €` becomes `114388`), localized formatting, per-currency decimals and an explicit rounding helper (nearest, ties away from zero).
- Accounts: create, edit and archive accounts (name, kind, currency, opening date and balance) from the `/accounts` screen. Archived accounts are hidden from the active list and kept for history.
- Deposit ceiling and overflow chain: an account can have an optional ceiling and an overflow account. A pure function splits a transfer along the chain and reports the unplaced surplus, saving refuses cycles, other currencies and archived targets, and an account used as an overflow account can neither be archived nor change currency until the references change. Corrupted chains are evaluated defensively and never loop.
- Transactions: expenses, incomes and interest entered by hand with an optional note and payment mode, edited and deleted from the `/transactions` screen. A transfer is two linked transactions of opposite sign, recorded and deleted together, and it cannot be edited. Computed account balances are shown on `/accounts`.
- Manual transfer above a deposit ceiling: the split is shown before recording, with the choice to cancel, deposit only the room, or send the surplus to a chosen account (the overflow account is preselected and the same room check applies). An income above a ceiling is accepted with a warning, and interest is always accepted.
- Categories: create, rename and archive flat categories from the `/categories` screen, and the to-categorize queue that lists the entered transactions without a category (transfers never have one) with a picker to categorize each of them. The transaction form and list carry the category. Names are unique regardless of case, archived categories included, and an archived category stays on the transactions that already carry it.
- Archived categories: the `/categories` screen lists them apart from the active ones, each with a "Reactivate" button (no confirmation, since nothing is lost). A reactivated category is offered again in the pickers and the rules that point to it apply again at the next import. The wording of the archive confirmation no longer says that it cannot be undone.
- Monthly synthesis: net of the month, savings of the month, cumulative savings and cumulative account, and end-of-month balances per account with a total in the reference currency, on the `/synthesis` screen. The figures reproduce the worked example of the sheet (cumulative account 2.98 then 159.05). Accounts in another currency are shown in their own currency and left out of the totals until exchange rates exist.
- Internationalization: the whole interface is available in French and English (`messages/fr.json`, `messages/en.json`). The language is chosen with a selector in the header (cookie), then the browser preferences, then English. Amounts, dates and months are formatted for the language. Adding a language only requires adding a translation file (see CONTRIBUTING).
- Confirmation before archiving an account or a category and before deleting a transaction or a transfer, in a native dialog that opens on the safe answer.
- CSV and OFX import from the `/imports` screen: choose an account and a file, check a preview (new transactions, duplicates ignored, rows that cannot be read, ceiling warnings), then import. A CSV file is read through a column mapping (separator, date column and format, label column, one signed amount column or separate debit and credit columns) that is guessed from the header row when possible and remembered for the next import on the account. Files up to 20 MB are read as UTF-8 or Windows-1252, parsed and never executed, and amounts are read without floating point. Importing the same file twice adds nothing, imports are recorded as batches, and imported transactions wait in the to-categorize queue. An income above a deposit ceiling and a movement on an archived account are accepted with a visible warning. Nothing is imported while a row of the file is invalid. The same movement exported again in the other format (CSV after OFX, or the reverse) is recognized, and a saved CSV mapping is only reused when it reads the new file, otherwise the one guessed from the header row is tried. Errors name the line of the file. Without a bank identifier, a movement identical to an earlier one that first appears in an export starting between them is ignored as a duplicate.
- Authentication, always on, for a single account. The account is created on `/setup` with the one-time token `DEMAIN_SETUP_TOKEN` and the page is closed once it exists (the table itself refuses a second row). Passwords are hashed with argon2id, error messages are generic, and the login and second-factor steps are rate limited per client address. Sessions are server-side (only a hash of the cookie token is stored), the cookie is `HttpOnly`, `Secure` and `SameSite=Lax` (with the `__Host-` prefix in production), and no token reaches `localStorage`. Optional TOTP with ten single-use backup codes is managed on `/security`, and turning it on or off asks for the password again. A proxy denies every page without a complete session, and each page and server action checks it again, and the origin check of Server Actions covers CSRF. `npm run auth:reset-password` resets the password on the host and signs out every session. Needs the new `DEMAIN_SETUP_TOKEN` variable until the account exists.
- Categorization rules: conditions on the label of a transaction (contains, starts with, equals, case-insensitive), optionally restricted to one account, evaluated in a user-defined order where the first matching rule wins. They are managed on the `/rules` screen (add, move up or down, delete after a confirmation) and applied at each import, where a matching row takes the category and the others wait in the to-categorize queue. A rule never changes transactions already recorded, and a rule pointing to an archived category is skipped. When a transaction is categorized by hand, an optional block offers to create a rule from its label (text and condition can be edited first), recorded in the same operation as the category so that either both happen or neither does.
- Balance assertions: record the balance shown by the bank for an account at a date from the `/accounts/[id]/balances` screen (a "Balances" link on each active account). Each recorded balance is compared with the balance Demain computes at the end of that day and the unexplained gap (computed minus recorded) is shown with a sentence saying who holds more, never by color alone. An assertion is per account, cannot predate the opening of the account, is refused on an archived account (the ones already recorded stay listed), and recording the same day again replaces the earlier value. Amounts are read without floating point.
- One-time migration of the spreadsheet history from the `/migration` screen: choose the monthly tabs and the Summary tab exported as CSV, the checking account, the first savings account and the opening balances, check a preview, then migrate. The separator, the header, the date format and the columns holding the type, the category and the payment mode are detected from the files, so that any CSV can be read (a date without a year takes the year given or the one in the file name, shown to confirm). Each savings row is split along the overflow chain of the savings accounts (the first row of the worked example becomes 123.16 and 450.00), the real account balance of each month becomes a balance assertion, and one `equals` categorization rule is created for each (label, category) pair. The figures are recomputed from the new history and compared with the Summary month by month. Nothing is dropped silently: every column that is not found, every value that is not recognized and every row that cannot be read is listed with its file and line, the ones that would lose a row stop the migration, the others are to be read and confirmed. The migration is all or nothing, and it is refused when an account already has transactions.
- Multi-currency: a reference currency (EUR until changed) and dated exchange rates, managed on the `/currencies` screen. Rates are stored as exact integers scaled by 10^8 (`1.0821` is `108210000`), read from text without floating point and applied with integer arithmetic and the usual rounding (nearest, ties away from zero). A rate applies from its date until a more recent one, in either direction of the pair, and the monthly synthesis converts an account in another currency into the totals (balances at the end of the month, net and savings flows at the date of each transaction). A currency with no rate for the date is left out and reported. Fetching the daily reference rates of the European Central Bank is optional, off by default and only runs when the owner clicks the button: it sends one request to `ecb.europa.eu` carrying no data about the owner, and it never replaces a rate typed by hand for the same day.
- Several files at once on the `/imports` screen: choose two or more CSV or OFX files and each is read in turn, as if it had been sent alone. A file that cannot be read does not stop the others. A dialog then shows one card per file with every row (date, label, amount, and whether the account already holds it), each cell editable in place, and the rows that cannot be read are kept with what the file says so that they can be fixed. Each file is imported or cancelled on its own, and nothing is recorded before its card is imported (each file is its own import batch). Every edited text is read again on the server before anything is written. A single file opens the same dialog, and a CSV whose columns are not found goes back to the column mapping form.
- Checklist of the two critical end-to-end journeys (first-run setup then login, monthly import routine) to walk by hand in a browser on a throwaway instance, in CONTRIBUTING, with the synthetic statement of `tests/fixtures/`.
- Docker packaging: a `Dockerfile` producing one image for `linux/amd64` and `linux/arm64` (Node.js 24, unprivileged user, Next.js telemetry disabled, `scripts/`, `src/` and `drizzle/` included so that `docker compose exec demain node scripts/reset-password.ts` works), a `compose.yaml` with one service, one volume and the external proxy network (no published port, the data directory pinned to the volume), a workflow that builds the image on pull requests and publishes it to the GitHub Container Registry for each version tag, the `docker` ecosystem in Dependabot, and the installation guide with a Caddy example and the list of what any reverse proxy must do. The container stops at startup when a required variable is missing.
- The real chart, on the home page: the month-end totals of the checking accounts and of the savings accounts, from the first month to the last complete month, in the reference currency, real values only. It is hand-written SVG built on `d3-scale` and `d3-shape` (new dependencies, with their type definitions). The two series are told apart by a marker shape (circle and square) and a legend as well as by color, the chart has an equivalent data table, and it is one tab stop that is read month by month with the arrow keys, Home and End (or by pointing), the month being announced in a live region. The monthly synthesis now also returns its total split by kind of account.
- Backup and export, from the `/backup` screen. An encrypted snapshot of the database (SQLite online backup, so the app keeps running; argon2id key derivation and AES-256-GCM in a versioned file, password of 12 characters at least typed twice) is the file to keep off-site and the one to restore from. Restoring asks for the snapshot password and the current account password, then for a confirmation, checks the file before touching anything (password, integrity, made by Demain, not from a newer release, valid overflow chains), replaces the content of the database, applies the migrations the snapshot predates, signs every session out and keeps what was replaced as `before-restore.db`. A JSON export with a documented, versioned schema (`docs/export.schema.json`) writes amounts as integers in minor units with their currency code, never carries the credentials of the account, is plain by default with a visible warning, and can be encrypted with a password. The JSON export cannot be restored. A volume backup procedure (stop the container, archive the volume) with its restore is documented and was run with Docker, in `docs/BACKUPS.md`.
- Security headers on every response: a `Content-Security-Policy` with a per-request nonce, and static `Strict-Transport-Security`, `X-Content-Type-Options`, `Referrer-Policy` and `Permissions-Policy`. Tests fail when an outbound call appears outside the opt-in rate fetch, and when a log line interpolates data.
- A "Skip to content" link, the first stop of the keyboard on every page. The manual axe and keyboard check is documented in CONTRIBUTING and found no violation on the main screens.
- Error and not found pages in the application shell and in the user's language, replacing the English default pages of Next.js. They show a generic message and a retry button, never the error: the detail stays in the server log.
- Toast notices for the result of every action, announced to screen readers (errors assertively, successes politely): accounts, categories, transactions and transfers, rules, currencies and exchange rates, balance checks, imports, sheet migration, backup and restore, second factor, sign in and out. Archiving or deleting says why it is refused instead of failing with an unhandled error, and a failed import or migration shows a generic message. See ADR-015.
- Type guessing for imported rows, in the pure domain: an explicit type cell, the debit and credit columns or the sign of the amount, the vocabulary of the category and the history of the label are tried in layers, each guess carries its evidence and a high, medium or low confidence, and only a low confidence is flagged to confirm. The default vocabulary is fixed, in French and in English. The import dialog shows the type of each row and, for a low confidence, the reason in text.
- Reading of any CSV file, in the pure domain: the decimal mark is read per file (`1.234` is a thousand in a file that writes `-12,50`), lines above the header, total rows and a summary block beside the table are ignored and reported with their lines, and the type, payment mode, category and description columns are found from their header words before their values (`CB`, `PRLV` and `VIR` are read as payment modes). A row with no label takes its category as label. The import dialog reads its files with it; its notices (columns ignored, values not recognized, assumed year, total rows ignored) are not shown yet.
- Overflow account chosen during an import: when a savings row exceeds the ceiling of an account that has no overflow account, the review dialog shows the amount that does not fit, in text, and asks which account takes it. The choice is only remembered in the dialog: the account chosen becomes the overflow account of the savings account for good when a file is imported, in the same transaction as the import, so closing the dialog or a refused import leaves no link behind. The dialog asks again only if that account is full in turn and has none. A savings-type account in the currency of the savings account can be created from the same place, and is created with the import too. A choice the ledger refuses (loop, archived or foreign-currency account) refuses the whole import with a message in the card, and each file of a multi-file import carries the choices, which an earlier file may already have saved. The usual rules apply (no cycle, same currency, no archived target), and the account that receives the file is not offered.
- Savings rows in an import: a row typed as savings is recorded as linked pairs of transfers, split along the overflow chain from the current balances, and a positive savings row is a withdrawal from the savings account. Rows are taken in date order, and each file is one batch, deduplicated against the account and recorded all or nothing: a part that fits nowhere, a loop in the chain or a row the ledger refuses blocks the file. The import dialog shows it (see the review dialog below).
- Import dialog with accounts and savings: any file chosen on `/imports` opens the review dialog (a CSV whose columns are not found still goes back to the column mapping form). Two selects sit at the top: the account that receives the files, which reads the files again when changed (duplicates and currency depend on it; the edits made on the rows are kept, see below), and the savings account, preselected with the head of the overflow chain when there is exactly one and limited to the active savings accounts of the same currency other than the receiving account. Each row has an editable type (expense, income, savings), category (not for savings), payment mode and, for savings, its own savings account. A savings row shows its split in text before the import ("€100.00 to Savings A, €200.00 to Savings B", or "€50.00 from Savings A" for a withdrawal), including the part that fits nowhere. The files are listed by their first date and each is planned from the balances the previous one leaves, so the "Import this file" button of a card stays disabled, with a sentence naming the file, until every earlier card is imported, cancelled or failed. A row whose type was guessed with little evidence reads "To confirm" with the reason in text, an unreadable row keeps its raw date and a type that contradicts the sign of the amount is marked "To confirm" with its reason (see Changed). When the ledger refuses a file, the dialog lists what blocks it and nothing is recorded.
- Column, selection and filter controls in the import dialog. Each CSV card has a "Columns of this file" block with one select per role (type, payment mode, category, description), set to the column the detection found: choosing another column, or "No column", reads the file again on the server with the same reader and recomputes its rows (the changes made to its rows follow their line in the file, see below). A column is offered to one role at a time. Every row has a checkbox with a label, a checkbox in the header selects all the rows shown, and the number of selected rows is announced as text. A group form changes the type, the category or the savings account of the selected rows at once, with the rules of a single row (the sign follows the type and a contradiction is marked "to confirm", only expenses and incomes take a category, only savings rows keep a savings account). A checkbox shows only the rows to confirm; the count of the file, the number of rows shown and the filter use the same definition. Focus is given back after a new reading, after a group change and when the last row to confirm leaves the filter.
- Corrections survive a column change or an account change in the import dialog. The type, category, savings account and texts a user changed on a row are tied to its line number in the file and applied again after the file is read with another column, or after every file is read again for another receiving account, even if the row moved in the list. A correction whose line the new reading no longer has is dropped, and the card says in text how many changes were kept and how many were dropped, until the next change made to the file. If reading again fails, the card shows the error as an alert, keeps its rows, and its "Import this file" button stays disabled until a reading succeeds. A "Read the file again" button next to the error reads the file with the assignment shown, so going back to the earlier columns does not require choosing another value; the error disappears once the reading succeeds, and the focus goes back to the button (error kept) or to the title of the card.
- Known limits of the import dialog: there is no way to add an overflow account or create an account from the dialog (a part that fits nowhere only blocks the file), no proposed rules and no undo of a batch yet, the reading notices of the CSV reader are not shown, a CSV without a header and a currency column taken for a category are not handled, and a correct guess cannot be confirmed (a row stays "to confirm" until its type is chosen). Changing the account that receives the files reads every file again and drops the edits made in the dialog, but each file is read with its own column choices. The split displayed is computed in the browser by the same pure planner as the server, from the balances read when the files were read; the server plans again from the real balances at import and has the last word.
- Gap with the real balance at the end of an imported file: after a file is recorded, its card asks for the balance the bank shows at the end of the file and tells, in text, whether Demain holds more, less or the same. The end date is the last movement date of the file, and the typed amount is read without rounding.
- Balance assertion from the import review: a button records the real balance typed for the end of a file as a balance assertion dated on the last movement of the file, replacing an assertion of the same day.
- Repository structure: license (AGPL-3.0), `.github/` templates and CI skeleton, contribution and security policies.
- Import: once a file is recorded, the (label, category) pairs of its categorized rows are proposed as `equals` rules for its account. Nothing is created without selection, and pairs already covered by a rule are not proposed.

### Changed

- In the import dialog, an explicit type (the type column of the file or the one chosen in the row) wins over the sign of the amount: the row is recorded with the sign of the type (an expense is negative, an income is positive, the absolute value is kept), marked "To confirm" in text with its reason, and its file is no longer blocked. The amount cell shows the amount that will be recorded, and the duplicate fingerprints follow it. Savings are not affected.
- The monthly synthesis converts accounts and flows in another currency with the stored exchange rates instead of leaving them out, and its reference currency is the setting of the `/currencies` screen instead of a fixed EUR.
- Next.js is upgraded from 16.4.0 to 16.4.3, which fixes three advisories reported by `npm audit` (two unauthenticated remote code execution flaws in the image optimization API and in `use cache`, neither used by Demain, and a denial of service through Server Actions, which Demain exposes). The minimum version in `package.json` is raised to match.
- Archiving an account is refused unless its computed balance is exactly zero (a negative balance included). No transaction can be entered on, edited on or deleted from an archived account, and the currency of an account cannot change once it has a transaction.
- Field errors of the forms are announced to assistive technologies and focus moves to the first invalid field after a refused submit.
- Validation errors of the domain carry a translation key (`MessageRef`) besides their English message, and form errors are translated server side.
- "Today" and the current month of the transactions form and of the monthly synthesis follow the time zone of the server (`TZ`) instead of UTC.
- The sheet migration reads the type of a row without a type column with the layered guess: a file with no negative amount now gives expenses (it gave incomes), while a signed file still gives expenses for negative amounts and incomes for positive ones.
- The sheet migration reads files through the shared CSV reader: a tab with lines above its header, a total row or a summary beside the table is read without the unreadable rows they used to cause (each is reported), a row with no description takes its category as label and is reported to be read instead of being skipped, a header that names the type, the payment mode or the category now selects that column, the number format of the file settles amounts such as `1.234`, and an amount that breaks the format of the file is reported as unreadable instead of being guessed on its own.
- An incoming savings row is no longer guessed as an income to confirm: savings are accepted in both directions. The sheet migration keeps its single run and its all or nothing (ADR-016).
- The uniqueness of a category name regardless of case is also guaranteed by a unique index in the database, not only by the application.

### Fixed

- The deposit ceiling check of an import now counts the incoming transfers of the account that receives the file, as DOMAIN says: a withdrawal from savings that brings the balance above the ceiling is reported as a warning, and a deposit to savings earlier in the file frees room.
